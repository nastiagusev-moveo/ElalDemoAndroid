Day of Travel & the old timeline

There are two screens that describe "my flight". The old TimelineFragment (the "Flight Feed") is a RecyclerView of cards built on the client. The new Day of Travel screen is a Compose screen driven by the server's travel stage. One server flag decides which one the app uses, and it also swaps the whole bottom tab bar.

The switch

One flag, two experiences

ConfigurationList.dayOfTravelEnabled comes from GetAppData and uses the same display-mode codes as the homepage flag (see part 2): 0 everyone, 1 youth, 2 adults + guests, 3 nobody, negative = everyone. AppConfig.DayOfTravel turns a missing value into 3, so missing means off.

    Day of Travel

    Data: the server decides the stage

    Day of Travel is server-driven. The server returns which flight, which travel phase, and whether the app should be "in control". The client renders that, with a fallback stage calculation when the server's block is stale.

    1
    Login brings the first block

    The DayOfTravel block arrives on LoginNEW, LoginByOTPNEW, MatmidLoginNEW and GetMatmidDetailsBySession. SaveUserDetailsUseCase stores it in DayOfTravelHolder. That's why the bar's chip and the open-on-launch decision are available instantly.

    2
    POST Application/GetDayOfTravelContent refreshes it

    Request: UserID, IsGuest, LanguageCode, PNRNum, FlightNumber, UDID. With PNR + flight number left null, the server picks the closest flight. Response: CurrentPhaseIndex, PnrNumber, FlightNumber, IsWithinTravelWindow, BaggageCarousel, Phases[]. Each phase has Stage, FlightAlerts, FlightDetails, EmptyState and Modules.

    3
    All calls go through RefreshDayOfTravelContentUseCase (a singleton)

    Unnamed "closest flight" refreshes run after login/PNR fetches, after a delete, on app resume and from the Trips list. Calls already in flight are shared, a mutex orders the writes, and only an OK response is published. A named call (fetchForBrowsedFlight) loads one tapped flight and never overwrites the tab's block.

    4
    DayOfTravelHolder: two slots

    closestFlightContent is the tab's own flight and drives the chip. content is what the screen shows, which can be a browsed flight while the user looks at a tapped one.

    "In control" is the server's call, not the client's.isDayOfTravelInControl is just IsWithinTravelWindow == true, and a missing value means "not in control". The backend decides the 48h-before / after-landing window. PNRFlightResponse.isWithinDayOfTravelControlWindow (48h before, 24h after landing) is dead code with no callers. Don't revive it.

    Which flight the tab shows (DayOfTravelFlightSelector)

    1. While browsing, the tapped flight wins.
    2. Otherwise, the flight the server named in its block. It is matched by PNR + flight number, then PNR only, then number only.
    3. Otherwise, the earliest departure among eligible flights: not another airline's, status Confirmed / Check-in / Flown / Stand-by, and not more than 24h after arrival. There is no minimum distance, so a flight months away can be picked.

    Bookings come from PnrHolder.pnrList, or the login's current flight when that list is empty. isSelectedFlight() lets the homepage and Trips jump to the tab instead of opening a second copy of the same flight. The module keeps its own copy of these rules in FlightUseCase.select.

    Day of Travel

    The screen

    DayOfTravelFragment hosts a ComposeView rendering DayOfTravelScreen. DayOfTravelViewModel is an MVI view model (contract in DayOfTravelContract.kt). Everything is in dayoftravel/src/main/java/il/co/ewave/elal/dayoftravel/.

    States

    • Loading: spinner (browsed flight).
    • Refreshing: hero + card skeletons, scrolling locked.
    • No flight: server-driven empty state (with "add flight").
    • Error: static screen, no retry button (by design).

    Refresh triggers

    • App comes back from the background (process start/stop).
    • Screen resumes (it reloads a browsed flight if the tab took the content back).
    • Returning from a web link that may change the booking (re-reads the PNR).
    • The countdown ticks every 1 second.

    Stage fallback: if the server's block is missing, names another flight, or has stage None, the view model derives a stage on the client (FlightUseCase.resolveStage: 24h before, 60/20 min boarding, 30 min before arrival) and asks for a refresh. logStageDecision logs which one won. Analytics: DayOfTravelAnalyticsManager (screen view, component clicks, carousel swipe, scroll, errors), group day_of_travel, process above_48/below_48. Hero images are preloaded into Coil from ElAlApplication.onCreate.

    Data & refresh

    1
    The argument: TimelineItem

    pnrIndex, flightIndex, isHomeTabTimeline, isHostedInHomeGraph. Resolved against the in-memory PnrHolder. On the Home tab it uses the login's current flight; otherwise pnrList[pnrIndex].flights[flightIndex].

    2
    PnrHolder is filled by ActivePnrUseCase

    It calls Reservation/GetUserActivePNRsNEW (skipped for guests), and calls HomeFragmentWrapperHelper.signalReset() when the Home tab's flight appears or disappears.

    3
    Refresh after web flows

    Manage booking, change seat, add baggage, check-in and the boarding-pass web fallback set isNeedToRefreshPnrData. On resume it re-fetches with Reservation/GetPNRByNumNEW and rebuilds the list. The new homepage's "My Flights" copies this pattern.

    4
    Boarding poll every 2 minutes

    BoardingDataFetcherUseCase calls Reservation/GetBoardingData only when departure is under 120 minutes away and boarding isn't closed or flown. It updates the boarding row and swaps baggage for baggage tags. All jobs are cancelled in onPause.

    Common traps

    Gotchas & known issues

    Found while reading the code. None of them have been changed.

    Stale comments Several Day of Travel KDocs no longer match the code
    DayOfTravelFragment says it takes no arguments, but the view model reads TIMELINE_ITEM. DayOfTravelViewModel says "60s ticker" / "3h after landing", but it is really 1 s / 24 h. DebugManager mentions a non-existent hasFlightWithinControlWindow. DayOfTravelStage mentions a non-existent DayOfTravelStageResolver (the logic is in FlightUseCase.resolveStage). Trust the code.
    No retry Day of Travel error screen
    The error screen deliberately has no retry button. The next refresh trigger (resume, back from background) reloads it.
    Not finished V1 stubs
    Some reservation CTAs only log ("UI only V1"). The flight-details sheet's calendar, manage-booking and share callbacks are not wired up. Connection and Foreign stages have no dedicated hero and fall back to PRE_TRIP. Booking confirmation defaults to "confirmed". Cancelled flights are out of scope. Lounges isn't modelled.
    Server vs client Same flight, different stage on tab vs browsed
    The tab uses the server's closest-flight block. A browsed flight uses a named call. When a block is stale, the client derives a stage. logStageDecision in the view model logs which source won. Read it before filing a "wrong stage" bug.
    Timeline nav Sub-screen taps from Live Update / React Native / Matmid (unverified)
    With the flag off, these entry points open the main graph's timelineFragment via action_global_timelineFragment. That destination declares no sub-screen actions, and navigateSafe swallows navigation errors. So tapping boarding pass / documents / baggage tags from a timeline opened this way may do nothing. Check on a device.
    PnrHolder Index fallback and a !!
    getPnrFlightByTimelineItem sets flightIndex = 1 (not 0) when it is negative ("white screen" fix), which returns null for a single-flight booking. updatePnrResponseByTimelineItem logs a null timelineItem and then uses timelineItem!!.
    Refresh drops PnrByNumberUseCase
    An invalid PNR or flight number only logs and still makes the call. A refresh started while another is running is silently dropped.
    Analytics Timeline screen-view goes to AppsFlyer only
    The timeline is logged as Flight_Feed by MainActivityViewModel.logScreenViewByDestination, which only sends to AppsFlyer. The Adobe state trip_timeline is declared but never used. Clicks go to Firebase as inner_click. The rate-us check uses RatingConsts.TIMELINE.
    Pinned Navigation 2.5.3
    The Navigation library is pinned (see the note in app/build.gradle), which is why back-stack checks use getBackStackEntry in a try/catch instead of currentBackStack.
