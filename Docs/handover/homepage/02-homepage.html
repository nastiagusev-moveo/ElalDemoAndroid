Old homepage, new homepage, and the switch

The El Al app has two homepages living side by side: the original XML screen and the new Jetpack Compose screen. One server flag decides which one a user gets. This page explains both screens, exactly how the flag is resolved, and what the Home tab opens before either homepage is even considered.

The core idea

How the switch works

There is no separate "new home" screen in navigation. Both homepages are the same destination, homeFragment, and HomeFragment decides what to draw the moment its view is created.

1 · Server

Sends a number

GetAppData returns ConfigurationList.newHomePageEnabled, a display-mode code. It's fetched on the splash screen and kept in memory in AppData.

2 · Resolve

Code vs. user mode

AppConfig.Home turns a missing value into 3, then DisplayModeUseCase checks the code against the user's mode (guests count as adults).

3 · Render

One fragment, two UIs

HomeFragment.onCreateView: false → inflate the XML layout. true → return a ComposeView hosting NewHomeScreen.

The display-mode codes

Server valueMeaningWho gets the new homepage
missing / nullNot configured. AppConfig replaces it with 3.Nobody (old homepage)
0Show to everyoneEveryone
1Youth users only (mode 1)Youth only, but youth users open Youth World instead (see the simulator)
2Adults only (mode 2). Guests count as adults.Adults + guests
3Always hideNobody (old homepage)
any negativeTreated as "no value", so always showEveryone
Missing means OLD, not new.DisplayModeResolver on its own treats null as "show". The homepage never reaches it with null, though, because AppConfig.Home.newHomePageEnabled falls back to 3 first. The comment on the field in ConfigurationListResponse.kt ("any other value keeps the new Compose homepage") is also too simple: 1 and 2 limit it to one audience.

Everywhere the flag is read

WhereWhat it changes
HomeFragment.isNewHomeEnabledWhich UI is drawn, plus every lifecycle branch: Adobe pushState (old only), event subscriptions, onResume refresh, rate-us check (RatingConsts.NEW_HOME), cleanup in onDestroyView.
NewHomeViewModel.isNewHomeEnabledRead by HomeFragmentWrapper. With the old homepage, an upcoming flight takes over the Home tab (see next section).

Decision path
    Why "Youth (mode 1)" never reaches a homepage.Youth users are in Youth World mode (UserManager.isYouthWorldMode), and that is the wrapper's first rule. So flag value 1 ("youth only") gives the new homepage to people who never see the homepage. In practice it behaves like "nobody".
    Before the homepage

    The Home tab's gatekeeper: HomeFragmentWrapper

    The Home tab hosts a nested nav graph, home_wrapper_navigation.xml. Its start destination is a blank DummyHomeFragment, and the wrapper replaces it with the real start screen. The rules run top to bottom and the first match wins.

    1
    Youth World mode → youthWorldPreviewFragment

    No homepage at all.

    2
    Pending "open Day of Travel" request → dayOfTravelFragment

    Set at launch when the Day of Travel feature is on and the flight is inside the travel window (shouldOpenOnDayOfTravelTab), or when the user taps the Day of Travel tab. This applies to the new homepage too. It is one-time: the request is consumed here, so the next time the Home tab is built it falls through to the rules below.

    3
    Upcoming flight and the old homepage → flight takeover

    Day of Travel on → dayOfTravelFragment. Off → homeTimelineFragment. The new homepage skips this rule, because it shows flights in its own "My Flights" carousel. Day of Travel can still take over through rule 2.

    4
    Otherwise → homeFragment

    Here HomeFragment draws the old or the new homepage based on the flag.

    When is this decision made again?

    The wrapper remembers which "generation" it last built for (HomeFragmentWrapperHelper.resetGeneration). Any code that calls HomeFragmentWrapperHelper.signalReset() makes it decide again the next time it runs:

    TriggerCaller
    Loginauth/…/SharedLoginUseCase.kt (the wrapper also listens for SuccessLogin)
    Logoutapp/…/managers/LogoutManager.kt
    Youth / adult mode switchcore/…/YouthWorldModeSwitcherUseCase.kt
    Active flights changedcore/…/ActivePnrUseCase.kt
    Day of Travel tab navigationMainActivity.kt

    A brand-new wrapper instance starts at generation -1, so it always builds its graph on first use.

    New homepage

    The "My Flights" carousel

    When the user has an upcoming flight, the new homepage shows a swipeable row of flight cards in the hero's bottom slot, right under the search bar. This replaces the old homepage's habit of handing the whole Home tab to the timeline. Code: NewHomeViewModel.observeMyFlights() / buildMyFlights(), models in ui/fragments/newHome/MyFlight*.kt, UI in homeFragment/compose/MyFlights.kt.

    Data

    Same flights as the Trips tab

    It listens to PnrsFetcherHelper.activePnrsState (the stream the Trips tab uses) and reads PnrHolder.pnrList. Login, logout and refreshes flow through automatically.

    Refresh

    Ticks every 60 s

    The cards are rebuilt on every PNR update and once a minute, so the countdown and the destination's local time stay live while the homepage is open.

    Loading

    Skeleton card

    Shown while PNRs are loading and the user is expected to have a flight (currentFlightPnrResponse != null). That way a guest never sees a phantom card. Debug: IS_MY_FLIGHTS_SKELETON_TEST.

    Which flights get a card

    1
    Every flight of every active PNR

    Flights are flattened across all bookings, then sorted by departure time, not by booking order.

    2
    Waiting-list duplicates collapse to one card

    A passenger wait-listed in two cabins of the same flight gets one card. The key is flight number + departure date, and only waiting-list flights are de-duplicated.

    3
    Dropped cards

    A flight with missing legs or departure date. Any flight 3 hours after its scheduled landing, timezone-aware (didPassGraceWindowAfterLanding). A flight operated by another airline as soon as it is flown. The card stays visible during the flight itself.

    Comment vs. code: 3 hours, not 4.A comment in NewHomeViewModel.mapFlightToMyFlightItem talks about a "4-hour grace window after the scheduled landing". The constant HOURS_TO_KEEP_FLIGHT_AFTER_LANDING in PNRFlightResponse.kt is 3.

    Timing

    When a flag change reaches the user

    1
    Splash: FetchPromoAndAppDataUseCase calls GetAppData

    The ConfigurationList is stored in the AppData singleton, in memory only. Nothing else refetches it during the session.

    2
    Home content: FetchBasicDataUseCase calls GetHomepageContent

    Fills HomepageCarouselManager (old) and HomeSectionsManager (new) at the same time, so either homepage has its data ready.

    3
    Each time HomeFragment's view is created, the flag is read again

    The flag is a getter, not a cached value. Within one session the server value can't change, but the user's mode can (login, logout, youth/adult switch), and that changes the result when the code is 1 or 2.

    Changed the value on the server?Users see it the next time the app goes through the splash screen, which normally means a cold start. To check on a device, swipe the app away and open it again; backgrounding it is not enough.
    Hands-on

    Testing both homepages

    There is no debug switch for the new homepage in DebugManager. Day of Travel has one, the homepage does not. Pick one of these:

    Ask the backend to set newHomePageEnabled in the ConfigurationList for the environment you test on (dev / preProd / prod each have their own). Use 0 for everyone or 3 to switch it off. Then cold-start the app.

    With Charles or a similar proxy on a debug build, rewrite the GetAppData response so that ConfigurationList.newHomePageEnabled is 0 (new) or 3 (old). Cold-start the app so the splash fetches it again. This flips the homepage on your phone only, without touching the server.

    Temporarily hard-code the value in core/…/helpers/AppConfig.kt:

    object Home {
    val newHomePageEnabled: Int get() = 0   // TEMP: 0 = new for everyone, 3 = old. DO NOT COMMIT
}
    Never commit this.It overrides the server for every user of that build.

    Common traps

    Gotchas

    Flag missing Server didn't send it → old homepage
    The fallback in AppConfig.Home is 3 ("always hide"). If a new environment suddenly shows the old homepage, check that newHomePageEnabled is present in ConfigurationList first.
    Home tab shows timeline "Where did the homepage go?"
    With the old homepage and an upcoming flight, the wrapper puts the timeline (or Day of Travel) on the Home tab instead of the homepage. That's expected. The new homepage has no timeline takeover, but Day of Travel still takes over at launch when the feature is on and the flight is inside the travel window.
    Section missing A new-homepage section doesn't appear
    The new homepage has no local content: an empty list hides the section. Items are also filtered by IsActive and DisplayMode (visibleToUser()), so an item set to "youth only" disappears for adults and guests. Check the CMS item, not the app.
    Order ignored Section order looks wrong
    Order = 0 means "unplaced", not "first". Unplaced sections come after all numbered ones, in HomeSectionType declaration order. The first visible section moves into the hero slot when the user has no flight.
    Value 1 "Youth only" shows the new homepage to nobody
    Youth users go to Youth World before the homepage is considered. Use 0 or 2.
    Value 2 + mode 0 Some logged-in users still get the old homepage
    A user whose mode is 0 ("youth and adults") only matches codes 0 or negative. With 2 ("adults only") they get the old homepage.
    Deep link Back Back from Flight Tracker lands on Menu
    That's the old-homepage behaviour: "no history" screens are hosted on the Menu tab. With the new homepage they are hosted on Home. See MainActivity.navigateToFeatureHostTabNoHistory().
    Duplicate Menu Hamburger on the new homepage
    The header hamburger is shown only when the Day of Travel tab bar is on (isDayOfTravelTabBarEnabled). With the old tab bar the Menu tab exists, so the hamburger is hidden on purpose.
